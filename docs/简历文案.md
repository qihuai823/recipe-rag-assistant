# 简历文案（食谱 RAG 项目）

> 用途：放进「个人项目」栏。项目是**复现 + 二次开发**开源教程 C8，文案里必须保持这个措辞，否则面试被问「哪部分是你写的」会答不上来。

## 版本 A：4 条（推荐，适合一页简历）

**食谱 RAG 问答助手｜个人项目｜复现并二次开发 datawhalechina/all-in-rag（C8）**

- **场景拆解**：面向「今天吃什么」把提问分成两类——「有什么简单的素菜」是筛选型，「宫保鸡丁怎么做」是细节型。前者要求按分类/难度精确过滤后出列表，后者要求召回具体菜谱的完整步骤，因此做成两条检索链路而非一套流程。语料 323 篇菜谱，结构感知分块后 1764 个块。
- **检索策略迭代**：初版沿用「先取 top-k 再过滤」，实测难度条件满足率只有 0.50——候选池里没有符合条件的菜谱就被判为无结果。改为「先在元数据上筛子集，再在子集内做向量 + BM25 + RRF」后升到 1.00，端到端延迟从 4.54 s 变为 4.52 s。
- **兜底与预期管理**：过滤后为空时先放宽难度、再退化为混合检索，并在回答开头明确写出「当前语料没有完全符合条件的菜谱，以下是放宽后的推荐」，避免用「没有」糊弄用户；空结果率降到 0。
- **可验证的评测**：脚本从语料自动生成 21 条评测集（15 条细节型 + 6 条筛选型），定义召回@3、分类/难度约束满足率、空结果率、P90 延迟四项指标，做「有没有元数据过滤」的对照实验：分类满足率 0.00 → 1.00，筛选型平均耗时 0.7–1.2 s、整体 4.5 s。失败案例与口径写进评测报告。
- **交付**：配置全部走环境变量、不出现硬编码密钥；本地模型优先（弱网可跑）；零依赖 Web Demo（标准库 http.server + 单页前端）；按 CC BY-NC-SA 4.0 注明来源。

## 版本 B：2 条（简历空间紧时）

- **食谱 RAG 问答助手（复现并二次开发 all-in-rag C8）**：把用户提问拆成「筛选型/细节型」两条链路，筛选型用分类 + 难度做检索硬条件；发现「检索后过滤」会因候选池遗漏导致难度满足率仅 0.50，改为「先筛子集再混合检索」后升至 1.00，延迟基本不变（4.54 s → 4.52 s）。补充两级兜底并在回答中显式提示已放宽条件，空结果率归零。

## 面试要能讲清的 6 个点

1. **为什么「过滤前移」有效**：原来的过滤发生在向量 + BM25 各取 5 条之后，候选池只有 10 条，符合条件的菜谱可能根本不在池子里；前移后 FAISS 用 `filter=` 在子集内检索、BM25 也在子集内建索引，等于扩大了候选范围。代价是每次查询重建一次 BM25（1764 文档，实测整体延迟无变化）。
2. **0.50 → 1.00 具体是什么**：筛选型问题 6 条里，初版有 3 条返回的菜谱难度与用户要求不符（因为放宽了难度）；改完后 6 条全部命中正确难度。
3. **为什么不直接上 rerank**：ColBERT/cross-encoder 会增加模型体积与首字延迟，而当前问题不是「排序不准」而是「候选集错了」，先修检索层性价比更高。这个判断在报告里有对照数据支撑。
4. **「咖喱炒蟹」为什么总在第 2 位**：短文档 + 高频词导致向量相似度偏高，属于典型干扰项；诚实说法是「需要 rerank 或长度归一化，我还没做」。
5. **21 条评测集的局限**：只能支撑「改动前后相对比较」，不能说成线上效果；样本量、标注方式是自动生成（分类来自文件夹名、难度来自星数解析），不是人工标注。
6. **延迟 4.5 s 的取舍**：路由 + 改写各一次 LLM 调用占大头，检索本身 1 s 内；优化方向是合并成一次调用、加缓存、列表型走流式/骨架屏。
