1. 详情型 recall@3 = 0.978：45 条里 1 条未命中 top3（D01 罗宋汤，检索返回陈皮排骨汤、话梅煮毛豆），但 `answer_hit` 仍是 1.00——生成侧会明确说明食谱缺失并给出 alternatives，不误导用户。
2. 列表型 11 条在检索前过滤下分类、难度约束都是 1.00，平均推荐 4.09 道不同菜，`list_has_three` = 1.00（每条至少给 3 道），空结果率 0。
3. 差距集中在列表型的约束满足：旧 21 条口径下不过滤时分类满足率 0.00（要「素菜」会返回荤菜、汤品），过滤下推到 FAISS/BM25 检索层后升到 1.00。
4. 早期的「检索后过滤」版本难度满足率只有 0.50——过滤发生在 top-k 候选池里，池子中恰好没有目标难度的文档就误判为空；把过滤下推到检索层后升到 1.00。
5. 端到端平均 4.52s、P90 6.33s，其中两次 LLM 调用（路由 + 改写）占主要部分，检索本身在 1 秒内。
6. 为什么要扩规模：21 条时单条波动就能左右整体通过率，看不出策略改动的真实影响；扩到 56 条后详情型 recall@3 从 1.00 回落到 0.978——这不是退步，而是小样本没暴露出来的边角案例。
